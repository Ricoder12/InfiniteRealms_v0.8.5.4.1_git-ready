## Reuse and work needed by the remaining v0.8.2 steps

### v0.8.2.2 — Guild receptionists and guildmasters

Reuse deterministic NPC IDs, saved NPC changes, schedule/presence checks, NPC relationship and memory records, and the occupation interaction router. Define how guild personnel map to a specific organization using existing NPC IDs and location references. Resolve the `.id` versus `.geoId` distinction explicitly. Do not add a second NPC/personality or relationship store. Ensure that the same individual remains linked when returning to a guild and through save/load.

### v0.8.2.3 — Membership services

Reuse the faction registry, eligibility checks, membership and standing fields, action routing, feed, and persistence. Decide whether the first release retains one membership per faction type or permits membership in a particular guild organization; current data only supports one global membership. Move join/leave/application choices into an appropriate local service interaction without silently changing current eligibility or standing rules. No per-organization membership exists yet.

### v0.8.2.4 — Contract board and acceptance

Reuse `JOBS` only for employment, personal-task objective patterns only where behavior genuinely applies, existing inventory/skills/travel/combat/time state, and the notification/feed system. The current faction contract handler cannot be used as an acceptance lifecycle because it resolves immediately. Add acceptance and a persistent active contract record only after deciding the contract-to-organization/faction references and objective rules. Keep objective completion, rewards, promotions, and rank advancement out of v0.8.2; completion belongs to v0.8.3.

### v0.8.2.5 — Guild reputation integration

Reuse faction-specific `factionStanding`; do not merge it with public reputation, legal heat, or NPC relationships. Centralize or carefully route new guild service changes through the existing field and retain legacy-key compatibility. Test that contract acceptance does not award standing early and that no duplicate standing changes are applied.

## Blockers, unresolved questions, and risks

1. **Organization records are service-derived, not full institution simulation.** A guild record exists at a generated `guild` service, but no leader, staff roster, rules, or service-specific membership exists.
2. **Guild-personnel availability is random.** A generic recruiter can occur in the deterministic guild pool, but not at every guild and there is no specialist identity guarantee.
3. **Single membership field:** Can the player join multiple separate adventurers’ guilds while remaining in one adventurers’ faction, or should v0.8.2 intentionally preserve the one-membership limit?
4. **Contract semantics:** At what point should a contract be bound to an organization versus the shared adventurers’ faction? The present “contract” is an immediate activity and provides no canonical definition of a contract board entry.
5. **Leader identity:** Which existing NPC ID should be the master/receptionist, and how should this be assigned without replacing/reseeding valid existing NPCs?
6. **Save migration:** New per-organization NPC references and any active contract data must survive normalization. The current normalizer rebuilds the world, so any mutable organization fields need explicit preservation and validation before those fields are introduced.
7. **Geographic references:** Organization records reference `geoId`; NPC schedules/actions mostly refer to site `.id`. Use a validated mapping, not string assumptions.
8. **No runtime verification:** This audit establishes code structure only. Schedule interactions, browser UI behavior, and real save/load behavior remain unverified here.
