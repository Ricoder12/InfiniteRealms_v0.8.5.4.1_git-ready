# Infinite Realms v0.8.6 — Regional Simulation Rules

**Status: approved for implementation.** The user explicitly approved these rules on 2026-10-24 before gameplay implementation began.

## Scope and state

- Keep `security`, `prosperity`, and `supplies` in the existing `world.v05.settlements[site.id]` records. Their range remains integer **0–100**; existing valid values are the starting values. Missing settlement records use the current v0.5 site risk, services, and settlement type formulas. Do not change `stability` or `population`.
- Add `world.v086` with `schema: 1`, `lastTickDay`, `lastTickSummary`, `regions[regionId] = { threat, resources }`, and `influence[siteId][factionId]`. Each valid geographic region ID, including a child region, has its own pool. A site uses its validated `site.regionId`; legacy missing IDs use the existing primary-region resolution. Parent regions do not automatically pool child resources.
- Threat, each resource pool, and each faction influence score are integers in **0–100**. Resource item IDs are exactly `bread`, `herb`, `wood`, and `ore`; these already exist in the market catalog. Faction IDs are exactly the five IDs in `IR_V08_FACTION_DEFINITIONS` (`faction:adventurers`, `faction:merchants`, `faction:royal`, `faction:arcanum`, `faction:shadow`). Influence is separate from character faction standing and polity ownership.

## Starting values and old saves

| Value | Deterministic starting rule |
|---|---|
| `lastTickDay` | Current `character.daysLived`; loading an old save performs no retrospective ticks. |
| Region threat | `0` with no active event; `max(0, 15 − daysInStage)` for an active warning; `max(0, 33 − daysInStage)` for an active escalation. An invalid event or stage gives `0`. |
| Region resource `itemId` | `min(100, 2 × N)`, where `N` is the number of sites assigned to that region whose existing biome lists an available gathering method with a gathering pool containing that exact item ID. No qualifying site gives `0`. |
| Settlement faction influence | For each canonical faction ID, clamp and round the corresponding existing `world.v05.factions[legacyId].influence` to `0–100`; missing or nonfinite input gives `0`. |
| `lastTickSummary` | `null`; the first simulation change in a new action starts a summary. It accumulates that action's net changes across every elapsed day and survives save/load. |

Valid saved v0.8.6 values survive load exactly. `lastTickDay` must be an integer from `0` through current `character.daysLived`; otherwise set it to the current day. An absent or non-`1` schema starts from all starting rules. For a missing or invalid individual field in schema `1`, use its starting rule while preserving valid sibling fields; an invalid summary becomes `null`. Ignore keys for unknown regions, nonsettlement sites, resource items, and factions. Invalid existing settlement condition values use the corresponding current v0.5 site formula, while valid values remain unchanged. If a site's explicit region reference cannot resolve uniquely, do not tick or trade for that site; report the invalid reference through validation. Loading does not create a market, advance time, alter a valid existing settlement value, or replay an old event.

## One tick per in-game day

Use `character.daysLived` as the day key. Process each unprocessed day once, in ascending order, including days elapsed in a multi-day action. Advance `lastTickDay` only after that day's state update succeeds. For each day, apply the existing event transition for that day, then these steps in order. The current event engine processes at most 365 days in one call; on a longer time jump, continue v0.8.6 ticks for every remaining day without creating additional event transitions.

1. **Threat:** `threat = max(0, threat − 1)` for every region. Existing event transitions also apply the one-time deltas below, clamped to `0–100`.
2. **Resource renewal:** For each region and each of the four items, add **1** if its qualifying site count `N > 0`; otherwise add **0**. Clamp to `0–100`. Gathering by the player is unchanged.
3. **Settlement pressure and recovery:** For each settlement in that region, read the region's threat after step 1. If threat is **30 or more**, change security and supplies by **−1** each. Otherwise, if threat is **10 or less** and security is below **60**, change security by **+1**. Then change prosperity by **−1** if threat is **30 or more**, security is below **40**, or supplies are below **25**. Otherwise, if threat is **10 or less**, security is **above 80**, and supplies are **above 75**, change prosperity by **+1**; otherwise change it by **0**. Evaluate prosperity after the security and supplies changes, and clamp each result to `0–100`.
4. **Trade:** Apply at most one qualifying transfer per settlement using its already existing market record, as defined below. A completed transfer changes prosperity by **+1**, regardless of units moved. Bread transfers change supplies by **+units** inbound or **−units** outbound. Clamp both to `0–100`.
5. **Weekly influence normalization:** On each day whose integer `character.daysLived` key is divisible by **7**, subtract **1** from every settlement faction score currently **above 50**. Scores at or below **50** are unchanged. Apply this once after the day's trade influence changes.

An event warning created after initialization adds **15** threat in its target site's region. Escalation adds **25**. A helped resolution subtracts **25**; an unresolved resolution adds **15**. Apply each transition once at its existing lifecycle point. Unknown or invalid event targets cause no new threat change. The existing event effects on site risk, settlement conditions, rewards, and standing still execute once through their current paths.

## Regional trade through existing markets

Only an existing market record at a settlement may trade, and the item must meet the current `ir04CanShop` rules at that settlement: bread/wood use the general shop, herb the alchemist shop, and ore the smithy. Do not initialize a market during a tick. Process settlements by stable site ID. For each settlement, try shortages first in the fixed order **bread, herb, wood, ore**; if none qualifies, try surpluses in that order.

- **Inbound, region → market:** Requires regional pool `> 0` and market `stock[item] < IR_V04_ITEM_DATA[item].stock`. Let `gap = normal stock − market stock` and `units = min(5, gap, regional pool)`. Move that many units: regional pool **−units**, market stock **+units**, and the item's existing market category demand becomes `clamp(demand × 0.985^units, 0.7, 1.5)`.
- **Outbound, market → region:** Requires regional pool `< 100` and market `stock[item] > IR_V04_ITEM_DATA[item].stock`. Let `gap = market stock − normal stock` and `units = min(5, gap, 100 − regional pool)`. Move that many units: regional pool **+units**, market stock **−units**, and category demand becomes `clamp(demand × 1.015^units, 0.7, 1.5)`.

For either completed transfer, set the existing market `transactions` count to `min(10,000,000, transactions + 1)` and leave `sales` unchanged; a multi-unit transfer is one transaction. A missing or invalid market, stock, demand, item definition, or shop service means no transfer. Player buying and selling continue through the existing market functions; this rule does not add an inventory, shop, price formula, or fee. The market's existing 30-day restock continues independently.

Example on a calm, non-weekly day after resource renewal: bread normal stock **10**, market stock **2**, and regional bread **7** yields an inbound **5-unit** transfer: market stock **7**, regional bread **2**, demand multiplied by `0.985^5`, supplies **+5**, prosperity **+1**, and merchant influence **+1**.

## Faction influence events

Apart from the weekly normalization in step 5, influence changes only through these verified actions at the relevant settlement:

| Verified action | Influence change |
|---|---:|
| Completed inbound or outbound regional market transfer | Merchants **+1** |
| Completed existing faction contract at a settlement | Contract's faction **+2** |
| Helped `security` regional event | Adventurers **+2**, royal **+2** |
| Helped `trade` regional event | Merchants **+2** |
| Helped `magic` regional event | Arcanum **+2** |

Unresolved events, failed help, contract acceptance, and ordinary player purchases/sales change no influence. Shadow influence can rise through its completed faction contract at a settlement. These scores do not change membership, character standing, guild rank, combat, or polity ownership.

## Action summary

`lastTickSummary` belongs to one outer UI action (`runAction` or an event choice), including every `dayPass` within a multi-leg journey or repeat action. A direct `dayPass` call outside a UI action forms its own action. Start a new summary only at the first committed v0.8.6 change of the next action; UI navigation and failed actions leave the previous summary visible. An event or contract change made after `dayPass` in the same action joins that summary. A paused route keeps only completed legs; resuming it later starts a new summary.

The summary stores `startDay`, `endDay`, `days`, net threat and resource deltas by region, net security/prosperity/supplies and influence deltas by settlement, plus completed transfer **count**, total **units**, and item/direction/site totals. Add each daily delta to the same summary rather than replacing it between days. Overwrite it on the next action that changes v0.8.6 state; do not append a permanent ledger. A failed or rolled-back tick contributes nothing.

## Visibility and compatibility

Show regional threat and four resource pools in the existing Living region panel. Show settlement security, prosperity, supplies, and five faction scores there, plus `lastTickSummary` when present. Keep the existing regional history for events and its **60**-entry limit; daily ticks do not append to it. Avoid a new tab or trade ledger. Keep market stock and demand visible in the current market panel.

Save `world.v086` through the current save path. Normalization is idempotent: two loads without elapsed game time produce the same v0.8.6 state and no trades. A failed validation or save must not leave half a daily tick applied. The current world, faction, event, market, party, combat, and player save fields remain compatible. The implementation must cover missing/invalid data, multi-day summary accumulation, tick replay prevention, regional assignment, event transitions, 1–5-unit trade in both directions, weekly influence normalization, and old-save load behavior in targeted tests.
