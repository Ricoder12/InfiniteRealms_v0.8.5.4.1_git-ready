# Infinite Realms v0.7.5.2 — Stable Geographic Identifiers

## Status and baseline

This is an additive identifier layer built from the accepted v0.7.5.1 source audit. The starting v0.7.3.6 standalone HTML is preserved at `backups/InfiniteRealms_v0.7.3.6_baseline.html`. No new continent, country, kingdom, faction, biome, settlement, or route was generated. The 7×7 / 49-site world layout, seed algorithm, route graph, biome assignment, settlement placement, risk, travel durations, and encounter probabilities remain unchanged.

## Identifier strategy

- `world.id`: `world-<lossless encoded normalized seed>`. The seed is already normalized by the existing generator to a trimmed maximum of 32 Unicode code points. The encoding uses Unicode code points in hexadecimal, not a lossy hash, display name, or array index.
- `region.id`: `region:<world.id>:primary`. The current model has one generated primary region; this suffix leaves room for future scoped regions without implementing a hierarchy now.
- `site.geoId`: `site:<world.id>:<site.id>`. Existing `site.id` (`loc-row-col`) is preserved as the legacy local key. The new ID does not depend on `site.name` or the site's array position. It is stable across renames and array reordering, as long as the existing legacy site ID remains unchanged.
- `region.routes[].geoId`: `route:<world.id>:<sorted endpoint legacy site IDs>`. Endpoints are canonicalized so an undirected edge receives the same ID regardless of direction or array ordering.
- `region.routes[].fromGeoId` / `toGeoId`: stable site endpoint references. Existing numeric `a` / `b` array-index fields remain for compatibility.
- `site.routes[].geoId`: the same canonical route ID as the corresponding global edge; `toGeoId` adds a stable destination reference. Existing `to` (`site.id`) remains intact for current travel, NPC schedule, and other gameplay code.
- `world.geographicIdVersion`: `1` marks that the additive identifier layer has been applied.

The current `biomeId` keys are already stable semantic keys (`forest`, `plains`, etc.); no additional biome IDs were necessary.

## Compatibility adapter

`irGeoResolveGlobalRoute(region, edge)` resolves map-rendering route endpoints through the stable `fromGeoId` / `toGeoId` fields. It falls back to legacy numeric `a` / `b` only for pre-patch edges that do not yet have stable endpoint references. If stable references are present but unresolved or ambiguous, it returns `resolved: false` instead of silently choosing another site.

Only the two existing global route renderers were changed to use this helper:

- `mapPanel()` in `js/game/03-stability-v0.2.1.js`
- `ir05NaturalMapPanel()` in `js/game/06-talents-spells-factions-v0.5.js`

No travel duration, risk, encounter, route-planning, or local route behavior was changed. Local travel continues to resolve legacy `route.to` values using `site.id`.

## Initialization, migration, and validation

`generateProceduralWorld()` is wrapped to attach IDs after the original generator returns. `normalizeSave()` is wrapped to attach/verify IDs after the existing normalization and migration path completes. The existing save schema version remains unchanged; IDs are deterministic from the existing seed and legacy site keys, so old saves normalize to the same IDs without a save reset.

`irValidateGeographicIds(world)` is non-destructive. It reports missing IDs, duplicate site/route IDs, unresolved or ambiguous local route targets, invalid stable global endpoints, invalid legacy endpoint indexes when no stable endpoint exists, and stale known/visited/discovery/rumor references. It never removes locations or chooses an arbitrary duplicate. The save wrapper logs unresolved validation errors to the console; it does not reset the world.

## Known limitations

1. `site.id` remains `loc-row-col`; changing a site's legacy ID or moving a site to a new grid coordinate would change the derived `geoId`. This patch guarantees stability across display-name changes and array reordering, not an intentional redefinition of the site's legacy identity.
2. Other gameplay code still intentionally uses legacy `site.id` and `site.routes[].to`; they have not been globally migrated to `geoId`.
3. Legacy numeric route `a` / `b` values are retained and are still meaningful only against the original array ordering. The two map renderers use stable endpoint references when available. A future full geographic migration must identify any new consumer of numeric edge indexes before array reordering is used in production.
4. The current save normalizer rebuilds the seeded 49-site world and overlays selected saved fields. This patch does not change that behavior or broaden its persistence allowlist.
5. Actual browser startup and live save/load could not be exercised in the available browser environment; see the test report.
