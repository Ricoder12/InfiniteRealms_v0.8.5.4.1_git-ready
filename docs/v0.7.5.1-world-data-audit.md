# Infinite Realms v0.7.5.1 — World Data Audit

**Scope:** Audit only. No game code, data, UI, saves, migration logic, or generated world state was changed.

## Executive findings

The latest supplied standalone game is **v0.7.3.6**. The HTML identifies itself as that version, and its SHA-256 matches the `dist/infinite-realms.html` built file in the supplied source archive. I used that source archive to inspect the actual split JavaScript, not just the roadmap. Its script order in `index.html:13–56` is significant: legacy systems are loaded first, v0.7.2 systems wrap several earlier render/travel handlers, v0.7.3.1–.6 add further wrappers, and `27-boot.js` runs last.

**Current geographic model:** one generated `world.region` containing a fixed 49-node 7×7 site graph, one seed, biome metadata assigned per site, and one active location ID. This is a connected regional travel map—not a hierarchy of worlds, countries, subregions, or owned territories.

**What already exists:** deterministic seeded world creation; nine biome definitions; five settlement categories; location services and risk; connected routes; per-site exploration state; known/visited lists; discoveries and rumors; direct and multi-hop travel; seeded market records; location-aware NPC schedules; and local event, dungeon, bounty, and history references.

**What does not exist as a geographic data model:** stable `world.id` and `region.id`; country/kingdom/subregion records; a parent-child region hierarchy; settlement ownership/territory; terrain-cell or elevation data; a normalized route-edge identifier; and a first-class POI registry separate from the 49 site nodes. The older `REGIONS` constant is present but is not consumed by current code (see `js/data/world.js:8–14`; source search found no reference outside its declaration).

**Main compatibility risk:** geography is encoded in both IDs and array positions. Per-site routes point to IDs (`route.to`), but `region.routes` points to numeric array indexes (`a`, `b`). Multiple systems also rely on the 7×7 layout, fixed settlement indexes, `site.id`, `world.siteId`, and existing site fields. A geographic foundation should therefore be additive and adapter-based before any map/world expansion.

## 2. Actual data structures

### 2.1 World root

`generateProceduralWorld()` in `js/game/02-worldgen-v0.2.js:11–46` returns the following core shape:

```js
{
  seed,
  generationVersion: 2,
  region: { name, biome, desc, sites, routes },
  siteId,                 // player's active location; a site ID string
  visited: [siteId, ...],
  known: [siteId, ...],
  travelCount,
  startCircumstance,
  journal: {
    knownLocations,
    visitedLocations,
    discoveries,
    rumors
  }
}
```

`world.region` is one object. Its `name` is a generated display name, `biome` is the aggregate label `Mixed biomes`, `desc` is generated text, `sites` is the full 49-site array, and `routes` is the full route-edge array. There is no current `world.id`, `region.id`, `countryId`, `kingdomId`, `parentRegionId`, or geographic ownership field.

The runtime world root also accumulates separate feature records such as `world.economy`, `world.v05`, `world.v06`, `world.v067`, `world.v072`, and later `world.v073*` patch data. These are gameplay subsystems layered onto the world, not a geographic hierarchy.

### 2.2 Site / local location

Each object pushed by the generator (`js/game/02-worldgen-v0.2.js:15–26`) contains:

| Field | Actual purpose |
|---|---|
| `id` | Generated string `loc-${row}-${col}`. Unique within the generated 7×7 map, but not globally unique across worlds by itself. |
| `index` | Linear index `0..48`; also used to place settlements and resolve global route endpoints. |
| `row`, `col` | Grid coordinates, derived from the linear index. |
| `x`, `y` | Percent-style map coordinates, currently `8, 22, …, 92` for the 7×7 display. |
| `name` | Seeded display name. Other systems sometimes use name text heuristics, so treat it as mutable presentation data only in future design. |
| `icon` | Display icon. |
| `biomeId`, `biome` | Biome key and display name. Biome affects risk descriptions, gathering tables, loot/enemy choices, market demand, and map visuals. |
| `type` | `settlement`, `landmark`, or `wilderness`. |
| `settlementType` | `hamlet`, `village`, `town`, `remote`, `city`, or `null`. |
| `kind`, `risk` | Risk label and numeric risk. `kind` is derived from risk thresholds. |
| `desc` | Generated narrative description. |
| `services` | Service string array from `irServices()`, such as `inn`, `market`, `work-board`, `healer`, `stable`, `caravan`, `guild`, or `library`. |
| `opportunities` | Biome opportunity text copied from the biome record. |
| `routes` | Per-site outgoing route list; each route has `to` (destination site ID), `distanceKm`, `terrain`, `caravan`, `boat`, `shortcut`. |
| `discovered` | Boolean set by generation/travel and normalized from old data. It is not the authoritative map visibility check. |
| `visits` | Visit counter. |
| `changes` | Local mutable state: initially `scouted`, `searches`, `forageCount`, `clearedThreats`, `temporaryCamp`, `notes`; later actions attach other fields. The normalizer preserves only an explicit subset; see §5. |

There are no fields for latitude/longitude, elevation, tile topology, country/kingdom ownership, climate subzone, or parent-region ID.

### 2.3 Route representations

Two representations coexist:

- `world.region.routes[]`: `{a, b, distanceKm, terrain, caravan, boat, shortcut}`; `a` and `b` are **numeric site-array indexes** (`js/game/02-worldgen-v0.2.js:27–30`). Map rendering resolves them as `region.sites[e.a]` and `region.sites[e.b]` (`js/game/06-talents-spells-factions-v0.5.js:63–64`; later map wrappers are in `js/game/18-facility-polish-v0.7.2.js:78+`, `js/game/19-town-guards-inn-v0.7.2.3.js:143+`, and `js/game/20-occupation-depth-npc-crime-v0.7.2.5a.js:193+`).
- `site.routes[]`: `{to, distanceKm, terrain, caravan, boat, shortcut}`; `to` is a destination `site.id`. Travel, pathfinding, NPC schedules, and service logic mostly use this representation.

The generator creates symmetric per-site route records for every global edge. There is no stable `route.id`, nor ID-based `from`/`to` pair in the global edge list. This dual representation is a core migration risk.

### 2.4 Biomes and settlements

`js/data/world.js:17–27` defines nine `IR_BIOMES` entries: `forest`, `plains`, `mountain`, `swamp`, `desert`, `snow`, `coast`, `river`, and `woodland`. Each has `name`, `icon`, `risk`, `desc`, `opportunities`, and `terrain`. These are definitions, not connected geographic areas; each site receives one `biomeId` from the seeded biome deck.

`IR_SETTLEMENTS` at `js/data/world.js:30–36` keys settlements by fixed indexes: `0` hamlet, `6` village, `24` town, `42` remote settlement, and `48` city. `irServices()` in `js/game/02-worldgen-v0.2.js:8` maps the settlement category to available service strings. `irSettlementTitle()` creates display labels.

`REGIONS` at `js/data/world.js:8–14` contains five old fixed region definitions and four local IDs per entry (`square`, `market`, `forest`, `shrine`). It is not used by the active generator. These IDs do not match the generated `loc-row-col` IDs.

### 2.5 Discovery and journal data

The generator initializes `world.known`, `world.visited`, `site.discovered`, `site.visits`, each visited site's `changes.lastVisited`, and `world.journal` (`js/game/02-worldgen-v0.2.js:40–46`). The journal contains:

- `knownLocations`: site IDs.
- `visitedLocations`: site IDs.
- `discoveries`: records with `id`, `title`, `detail`, `siteId`, `date`.
- `rumors`: records with `id`, `targetId`, `title`, `text`, `resolved`.

`irRecordDiscovery()` also writes a separate, bounded copy to `character.discoveries` (`02-worldgen-v0.2.js:54–56`). `irAddKnownLocation()` updates both `world.known` and `world.journal.knownLocations` (`:57`). `irVisitLocation()` updates visits, last-visited day, discovery records, neighbor knowledge, and rumor resolution (`:58`).

Current world-map visibility chiefly checks `world.known` and `world.visited`, not `site.discovered` alone (`js/game/03-stability-v0.2.1.js:83–90`; natural-map renderer at `js/game/06-talents-spells-factions-v0.5.js:63–64`). So `discovered` is presently a supporting/redundant per-site flag rather than the map's single source of truth.

## 3. World creation and generation

### Functions and flow

1. `irHashSeed()` and `irRng()` (`js/game/02-worldgen-v0.2.js:4–5`) provide deterministic pseudo-random selection.
2. `generateProceduralWorld(seedInput, startCircumstance)` (`:11–46`) trims the seed to 32 characters, creates a shuffled 49-entry biome deck, and creates all 49 sites.
3. The generator lays out the sites in a fixed 7×7 grid (`:15–26`), assigning names and terrain from seeded arrays.
4. Five settlement kinds are assigned by the fixed numeric positions in `IR_SETTLEMENTS`.
5. A grid graph is built with horizontal and vertical links, optional diagonal shortcuts, three extra hard-coded links, and one extra route between two eligible wet-biome sites (`:27–30`).
6. Global `edges` are converted to the site-local `routes` lists. The ordinary lattice plus extra links is intended to keep the graph connected.
7. Starting position is selected by the `startCircumstance` switch: default index 24; `remote` index 42; `roadside` index 25; `wilderness` selects an eligible non-settlement next to a settlement, with index 25 as fallback (`:32–40`).
8. The start site is marked visited/discovered and the seeded journal and four rumor targets are initialized (`:40–46`).
9. `makeInitial()` calls the generator and constructs the initial character/world state (`:82–84`). Actual start-life flows wrap `makeInitial`/`startLife` in later scripts, so preserve script order when changing generation.

### Duplicate-generation and seed behavior

The generator is deterministic for a given normalized seed and circumstance. It always generates 49 sites. IDs are the grid coordinates, so for a given grid position the ID is identical across **different seeds**; the seed is not part of `site.id`. The world seed is therefore required to disambiguate a location across separate worlds.

The current generator has no independent world/region identity object. The generated region's display name is seed-derived, and the NPC key uses that display name as part of its identity key. No separate persisted generation registry prevents rerunning world generation; instead, save normalization regenerates the world from its seed and overlays selected saved fields.

## 4. Travel and exploration

### Travel

- `irSiteById(id)` (`js/game/02-worldgen-v0.2.js:48`) searches by `site.id`.
- `irRouteBetween(aId,bId)` (`:49`) looks for a direct route in the source site's `routes` array.
- `irCurrentTransportDays(distanceKm,transport)` (`:50`) uses rates of 20 km/day on foot, 42 mounted, 30 by caravan, and 34 by boat, rounded up with a one-day minimum.
- `irTransportCost()` and `irCanTransport()` (`:52–53`) check fare, route service, and transport availability.
- Base `travel(id,transport)` (`:92–93`) only executes a direct edge. It checks costs/energy, advances time, sets `world.siteId`, increments `travelCount`, calls `irVisitLocation()`, makes outgoing neighbors known, persists/renders, then rolls an encounter using the source/destination risk average and a transport modifier.
- v0.7.1 adds `ir071FindPath()`, `ir071RoutePlan()`, `ir071RouteEdge()`, and `ir071TravelRouteConfirm()` (`js/game/15-npc-schedules-v0.7.1.js:149–223`). It finds multi-hop paths with BFS through `site.routes[].to` and moves one edge at a time, which can stop early for hunger, energy, or an encounter. This later wrapper supersedes how non-adjacent travel requests are handled.

The normal World map only enables direct neighbors as travel buttons; a separate route-preview path can route to non-neighbor destinations. Route preview/confirmation currently plans the multi-hop journey on foot even though direct-edge travel supports other transports. This should be treated as existing behavior/dependency, not modified in the audit.

### Discovery

- At initialization, `known` contains the start site and direct neighbors; `visited` contains the start site.
- At arrival, `irVisitLocation()` marks a new site visited and discovered, increments `visits`, logs a discovery, makes neighbors known, and resolves matching rumor targets.
- Scouting and foraging use `site.biomeId`, `site.risk`, and site-local counters. `explore(mode)` is in `js/game/03-stability-v0.2.1.js:66–80`; foraging has biome-specific loot tables and a deterministic per-site/per-count RNG key; scouting reveals connected routes and can trigger encounters or discoveries.
- The journal has a cap of 80 discoveries; character discoveries are also bounded to 80. NPC/world timeline events in `world.v067.events` use `locationId` and `relatedNpcId` (`js/game/12-journal-world-history-v0.6.7.js:35–47`).

### Companion travel

There is no independent persistent companion-position graph. NPCs use scheduled site references; relationship companions are represented in relationship records and get a small energy-recovery benefit through a `dayPass` wrapper (`js/game/08-npc-foundation-v0.6.js:71–74`). That distinction matters: do not assume companions are autonomous world-map entities.

## 5. Save, load, and migration

### Current fields and entry points

- Local storage keys: `SAVE_KEY='infiniteRealms.v02.autosave'`, `SLOTS_KEY='infiniteRealms.v02.slots'`, with v0.1 fallback keys (`js/data/config.js:5–14`).
- `validSave()` and the original `normalizeSave()` are defined in `js/game/03-stability-v0.2.1.js:6–63`; `normalizeSave()` is subsequently wrapped by several later modules.
- Autosave read: `readAutosave()` (`js/game/02-worldgen-v0.2.js:74`); it reads current/legacy storage, validates, then normalizes.
- Manual slots: `readSlots()`, `writeSlots()`, `saveSlot()`, `loadSlot()` (`:75–78`). There are three slots. Slot metadata includes character name/race/age, region display name, and update time; full state is stored under `data`.
- JSON export/import: `exportSave()` and `importSave()` (`:79–80`), both using normalized state; import validates before replacing the current life.
- Startup: `boot()` is the final script's boot function (`js/game/27-boot.js:1`), which reads the autosave via `readAutosave()` and renders.
- Version metadata in the v0.7.3.6 save path is `gameVersion: '0.7.3.6'` and `saveSchemaVersion: 8` (`js/game/32-feedback-antifarming-regression-v0.7.3.6.js:418–439`). That is distinct from `world.generationVersion: 2` and the old intermediate `state.version` values.

### Current normalization model

`normalizeSave()` does not restore the saved 49-site array wholesale. The core normalizer:

1. Determines whether the input qualifies as a v2 generated world by checking `version >= 2`, `world.generationVersion === 2`, and at least 49 old region sites (`js/game/03-stability-v0.2.1.js:9–16`).
2. Re-runs `generateProceduralWorld(seed, circumstance)` (`:10–13`).
3. Validates `siteId`, `visited`, and `known` against IDs in the newly generated world (`:14–22`).
4. Reapplies each saved site's visits/discovery and a whitelist of `changes` fields (`:23–39`).
5. Reapplies rumor resolved flags by rumor ID and saved discovery entries (`:40–47`).
6. Replaces `s.world` with this rebuilt world, and then later normalizers reconstruct specific subsystems such as economy, NPC state, social history, event ledgers, and the v0.7.3.x ledgers.

This approach works because the current seed generator is deterministic and the site IDs/layout are stable. It is not yet a general migration system for arbitrary regions or a variable number of sites. For older non-v2 saves, the code creates a new generated world and appends a migration note; character stats, inventory, calendar, and chronicle are retained, but old static-map geography is not preserved as the same map (`03-stability-v0.2.1.js:62`).

### Save data gaps / cautions found

- **Local `site.changes` has an explicit allowlist.** `normalizeSave()` copies `scouted`, `firstScout`, `searches`, `forageCount`, `temporaryCamp`, `clearedThreats`, `notes`, and `lastVisited` (`03-stability-v0.2.1.js:28–36`). Later code attaches at least `site.changes.criminalIntel` (`19-town-guards-inn-v0.7.2.3.js:126`) and `site.changes.banditRewardDay` (`21-combat-theft-reputation-v0.7.2.5b.js:198`), neither of which is in that allowlist. Unless their relevant state is reconstructed from another persisted subsystem, those exact fields are at risk of disappearing through normalization/load. This is a pre-existing finding; this audit did not fix it.
- **ID validation can silently rehome data.** Invalid `world.siteId` falls back to the generated start site; visited/known IDs not present in the regenerated set are removed; invalid discovery `siteId` values are mapped to the current site or omitted in character discoveries. Adding a new ID scheme without migration adapters could cause location records to be discarded or reattached incorrectly.
- **NPC schedule IDs are corrected, not geographically migrated.** `ir071MigrateNPC()` adjusts invalid `homeSite`, `workSite`, `restSite`, and `socialSite` to available IDs (`15-npc-schedules-v0.7.1.js:20–45`). If site identities change, NPCs may be moved to fallback sites even though their NPC identities persist.
- **Rumor records are regenerated from the seed.** Normalization transfers the `resolved` boolean by rumor ID to regenerated rumors (`03-stability-v0.2.1.js:40–44`) rather than retaining arbitrary edits to each rumor's target/title/text. This relies on generator determinism and unchanged rumor-selection logic.
- **`site.discovered` is not enough to restore visibility.** The UI primarily consults `world.known` and `world.visited`; changes to those arrays must be migrated alongside site flags.

## 6. Location and identifier dependencies

The following are high-risk touchpoints for any future geographic ID/data migration:

| System | Exact dependency and source |
|---|---|
| Current location | `world.siteId`; `site()` looks it up in `world.region.sites`, then falls back to the first site if unresolved (`js/game/01-core-v0.1.js:5`). That fallback can mask a bad ID until normalization corrects it. |
| World/site identity | `site.id` is `loc-row-col`; NPC location key is `${seed}|${region.name}|${site.id}` (`js/game/02-worldgen-v0.2.js:25`; `js/game/08-npc-foundation-v0.6.js:5–9`). Changing seed, generated region display name, or site ID changes generated resident keys and can affect NPC identity continuity. |
| Grid assumptions | Exactly 49 sites; loops to 49; `row = floor(i/7)`, `col=i%7`, `x/y` formulas; index-based settlement placement; explicit start indexes 24/42/25 and fixed extra edges (`02-worldgen-v0.2.js:15–40`; `04-life-paths-combat-v0.3.js:62`). |
| Global routes and map | `region.routes[].a/b` are array indexes, used by map rendering (`06-talents-spells-factions-v0.5.js:63–64`; later `mapPanel` wrappers in 18/19/20). Reordering `sites` can draw wrong roads even if site IDs are retained. |
| Per-site routes and pathfinding | `site.routes[].to` is the destination ID, used by `irRouteBetween()` and `ir071FindPath()` (`02-worldgen-v0.2.js:48–53`; `15-npc-schedules-v0.7.1.js:149–179`). |
| Save migration | Core world normalizer requires `sites.length >= 49`, regenerates from seed, validates IDs, and copies a whitelist (`03-stability-v0.2.1.js:9–47`). Economy migration also accepts only market keys matching a current site ID (`05-progression-economy-v0.4.js:90`). |
| Economy | `world.economy.markets[siteId]`, each record's `siteId`, seeded market RNG `${seed}|economy|${siteId}|v04`, and biome/service-based demand (`05-progression-economy-v0.4.js:60–61, 90`). |
| Settlement simulation and regional events | `world.v05.settlements[site.id]`; settlement objects have `security`, `prosperity`, `supplies`, `stability`, `population`, `lastChangeDay`; `world.v05.activeEvent.siteId` locates an event (`06-talents-spells-factions-v0.5.js:25–29`). These are a single-region simulation, not country/kingdom geography. |
| NPC schedules | `homeSite`, `workSite`, `restSite`, `socialSite`, `ir071OriginSite`, `lastSeenSiteId`, all site ID references; path distances walk `site.routes[].to` (`15-npc-schedules-v0.7.1.js:18–45, 149–180`). |
| Relationships / NPC memory | NPC keys and `lastSeenSiteId`/location display derive from current site IDs and the location-keyed registry (`08-npc-foundation-v0.6.js:5–15`; `14-relationship-location-v0.6.8.1.js:9–39`). |
| Discoveries and world history | `journal.discoveries[].siteId`, `journal.knownLocations`, `journal.visitedLocations`, rumor `targetId`; world timeline `locationId` (`02-worldgen-v0.2.js:54–58`; `12-journal-world-history-v0.6.7.js:35–47`). |
| Bounties, crimes, active leads | `siteId` and `siteName` on crime/bounty/lead/event records; active bounties join back to a generated site ID (`20-occupation-depth-npc-crime-v0.7.2.5a.js:97–124, 265–276`). |
| Hunt / dungeon / warning | `state.hunt.siteId`, dungeon `world.dungeon.siteId`, and local warning/combat references are validated against `region.sites` (`04-life-paths-combat-v0.3.js:125–143`; see combat wrappers in 20). |
| Local service UI | Many screens check `site.type === 'settlement'`, `settlementType`, `services`, `biomeId`, `risk`, or match specific `siteId` values (`16-npc-occupations-v0.7.2.js:56, 76, 146, 150, 172–184`; `05-progression-economy-v0.4.js:60–61`). |
| Display-name heuristics | `ir06PoolFor()` derives NPC pool from regex matches in `site.id + site.name` such as forest/wood/fen/trail, market/square/crossing, mine/quarry, royal/castle, and guild/inn (`08-npc-foundation-v0.6.js:6`). Renaming sites can unexpectedly change resident occupation pools. |
| Static legacy IDs | `REGIONS[].sites[].id` uses `square`, `market`, `forest`, `shrine`; active generated IDs are `loc-row-col` (`js/data/world.js:8–14` vs `02-worldgen-v0.2.js:25`). Do not mix these without an explicit adapter. |
| Version/script order | `index.html:24–56` loads base worldgen, successive overrides, all six v0.7.3 patches, then boot. Testing a base function alone does not prove the last effective wrapper behaves the same. |

A further semantic mismatch: `travelCount` is shown as “journeys” but is incremented once for each completed route segment in `ir071TravelRouteConfirm()` (`15-npc-schedules-v0.7.1.js:211–213`), so a multi-leg trip can increment it several times.

## 7. Gap analysis against a geographic foundation

| Planned concept | Actual current state | Gap / design implication |
|---|---|---|
| Stable world identity | Seed string plus generated display name; no `world.id`. | Site IDs repeat across seeds; any stable location reference must be scoped by world identity/seed. |
| Regions / subregions | Single `world.region` with name, aggregate biome label, desc, sites, routes. | No nested region hierarchy or region membership for sites. |
| Countries / kingdoms | Absent as geographic ownership. `world.v05.factions` and `character.factionStanding` represent gameplay group membership/influence, not territory/country ownership (`06-talents-spells-factions-v0.5.js:22,26`). | Do not treat current factions as geography; add nothing at audit stage. |
| Biomes | Nine typed biome definitions assigned per site. | No biome polygons, adjoining biome borders, ecological zones, or terrain grid. |
| Terrain | Site-level `terrain` descriptor for route and biome; fixed abstract map coordinates. | No elevation, tile/hex cells, passability layer, river shapes, or terrain cost grid. |
| Settlements | `type`, `settlementType`, `services`, fixed site indexes, and `world.v05.settlements[siteId]` population/security/prosperity/etc. | Settlement identity is tied to site ID; settlement types are hard-coded at five indexes. |
| Points of interest | No separate POI registry. `landmark` is one of the `site.type` values in the same 49-node graph. Dungeon is a world/current quest state with `siteId`, not a general graph node registry. | Need to clarify later whether POIs are sites or child records; do not build a second registry prematurely. |
| Roads / paths | Connected graph. Global edges by array indexes; local edges by IDs. | No edge identity; two representations must stay synchronized. Geometry and travel graph are currently the same abstraction. |
| Travel | Direct edges plus BFS multi-hop path, risks, costs, time, energy, encounters. | Consumers rely heavily on old ID topology; route-preview path is foot-only. |
| Discovered / unknown | `known`, `visited`, journal arrays plus `site.discovered` and `visits`. | Redundant representations need a clear source-of-truth and migration rules before graph/schema changes. |
| Durable persistence | Rebuild generated world from seed and migrate selected fields. Save schema 8; world generation version 2. | Good for deterministic same-layout worlds, fragile for variable region/site counts or IDs. Site-local changes whitelist may drop newly added per-site data. |
| NPC continuity | Site ID plus seed and region **display name** compose resident generation keys. | A mere display-name change can change generated NPC location keys; stable IDs should replace presentation strings in identity keys only after migration is planned. |

## 8. Proposed minimal plan: v0.7.5.2–v0.7.5.5

This is a proposal only. No version beyond this audit has been started.

### v0.7.5.2 — Geographic identity design and additive metadata

- Define a documented identity contract for a world and the current region; choose deterministic IDs with an explicit scope (for example, seed/world key + region key), avoiding a display name as identity.
- Preserve `world.region`, `site.id`, `site.index`, `site.routes`, and existing generated geography unchanged. Add metadata only if it can be derived safely; do **not** re-key the live site list yet.
- Specify route-edge canonical fields (`fromId` / `toId` or a stable edge ID) while retaining numeric `a`/`b` fields as compatibility data. Do not change rendered map behavior.
- Deliver a schema note and pure helper(s); no new countries/kingdoms/factions, tiles, biomes, or content.
- Gate: deterministic identities; no changes to generated names, site IDs, route count, travel, or saved world snapshots other than additive metadata.

### v0.7.5.3 — Migration and persistence guard

- Add idempotent normalization for only the additive identity fields. Existing saves without the fields should derive them from their existing seed/current region/site values rather than regenerate a different map.
- Preserve current save schema 8 unless tests prove an actual schema bump is required. Keep `world.generationVersion` separate from save schema.
- Define migration behavior for invalid/missing current location, `known`/`visited`, rumors, discoveries, markets, NPC schedule locations, active events, hunt/dungeon, and site-local change records.
- Fix or explicitly preserve documented `site.changes` fields only within scope, and test the allowlist to avoid losing current state. Do not rewrite unrelated save systems.
- Gate: legacy/current saves normalize repeatably; same seed yields the exact existing map; second normalization produces no unintended diff.

### v0.7.5.4 — Compatibility accessors for geography consumers

- Introduce a minimal lookup/route adapter layer that accepts current site IDs and can resolve future canonical route endpoint fields with fallback to `a`/`b` indexes.

## 10. Known issues and audit conclusions

1. The active world is fixed at 49 locations and one region. A multi-country world cannot be represented without a data-model extension.
2. Array position is effectively part of the route schema through global `a`/`b` endpoints and map renderers.
3. A site's plain ID is only locally unique; deterministic location/NPC keys need world context.
4. Display text is used in at least one identity key and several heuristic NPC-pool selectors.
5. Save normalization regenerates the geography and only reapplies known fields; variable-size worlds and arbitrary per-site data are not safely supported yet.
6. The `site.changes` persistence whitelist omits `criminalIntel` and `banditRewardDay` even though handlers write them. This is a documented pre-existing risk, not a change made during this audit.
7. `site.discovered` and the map's `known`/`visited` lists overlap; future changes should preserve them consistently rather than choose one casually.
8. `travelCount` counts route segments in multi-hop travel while the UI labels it as journeys.
9. The fixed legacy `REGIONS` data is disconnected from active generated geography and uses incompatible IDs.
10. Existing factions are gameplay organizations/standing, not geographic countries or territorial control.

## Audit conclusion

The audit is sufficient to design a **minimal, additive compatibility layer**, but not to safely implement a country-scale or multi-region generator yet. The safest sequence is stable scoped identity → idempotent save migration → adapter-based consumer migration → broad regression lock. Preserve the 49-site generation and current IDs until the adapters and save migration have been proven with real save files. No v0.7.5.2 implementation has been started.
