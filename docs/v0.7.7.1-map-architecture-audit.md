# Infinite Realms v0.7.7.1 — Map Architecture Audit

## Scope and outcome

Audit the accepted v0.7.6.6 source (which includes the accepted v0.7.5.5 geographic foundation and v0.7.6.1–v0.7.6.6 biome ecology layers). This subversion adds a small read-only map-data access layer and tests. It does **not** implement world, regional, or local map views, change travel, regenerate saved worlds, or modify biome/ecology gameplay.

## Findings from actual source inspection

### Authoritative objects and identity

- `state.world` is the current saved world object.
- `state.world.region` is the single generated region currently supported by the generator.
- `world.region.sites` is the authoritative array of site/location records. Each current generated site has a legacy `id` and a stable `geoId` introduced in v0.7.5.2.
- `world.region.routes` is the global connection-edge collection. Each generated edge has a stable `geoId`, `fromGeoId`, and `toGeoId`, while retaining legacy numeric `a`/`b` endpoints and its distance/terrain/transport/shortcut properties.
- Each site also has `site.routes[]` entries with legacy `to` IDs and travel properties. This is a second, legacy per-site representation of connections used by current travel code. It is not a new registry; it is a compatibility duplication that should be handled carefully in a later approved migration.
- `world.geography` is an index of references (`regionIds`, `biomeIds`, settlement/POI references and connection references), not a second location database. It does not contain copied names, coordinates or route data.
- Stable geographic IDs are generated from world/legacy site IDs, not display names or array positions. The shared API rejects unresolved or ambiguous `geoId`s rather than guessing.

### Coordinates and physical geography

- Generated locations have `row`, `col`, `x`, and `y` values from the 7×7 layout. `x`/`y` are abstract percentage positions for the current regional map renderer, with current generated values spanning 8–92; they are not longitude/latitude or world-scale physical coordinates.
- There are no current `worldX`/`worldY`, latitude/longitude, continent outlines, river polylines, coastlines, road geometries or local settlement floorplans in the authoritative data.
- Route edges encode graph connectivity and route attributes (`distanceKm`, `terrain`, `caravan`, `boat`, `shortcut`). Terrain is presently a route label derived from connected sites, not a geometric terrain feature.

### Hierarchy and political data

- v0.7.5.3 provides stable `world.id`, `region.id`, `site.regionId`, nullable `continentId`/`countryId`, and stable settlement/point-of-interest IDs.
- The generator currently creates one primary region, with 49 sites. The `world.continents` and `world.countries` arrays are empty; region and site country/continent references are null. These fields are extension points, not populated political geography.
- No authoritative territorial borders or ownership data exists. No such data was invented in this subversion.

### Biomes, terrain, landmarks and settlements

- `site.biomeId` references the single `IR_BIOMES` registry. `site.biome` is a legacy display label; map data consumers should use `biomeId` and resolve the profile through `IR_BIOMES`.
- `site.type`, `settlementType`, `settlementId`, and `pointOfInterestId` distinguish wilderness, settlement, and landmark records. Settlement/POI indexes reference `siteGeoId` and do not duplicate site data.
- No separate river/road/terrain geometry layer exists beyond site biomes and route edges.

### Discovery and navigation

- Discovery is represented in more than one compatible field: `site.discovered`, `world.known[]`, `world.visited[]`, journal known/visited lists, and discovery/rumor records. Current map rendering primarily uses `known`/`visited`; `site.discovered` is also persisted.
- The current map renderer is `mapPanel()` in `js/game/03-stability-v0.2.1.js`. It renders all 49 sites in a regional-style map, uses `site.x`/`site.y` for placement, `world.region.routes` for lines, and legacy IDs for visibility/current/neighbor checks.
- Current travel/navigation helpers are in `js/game/02-worldgen-v0.2.js`: `irSiteById`, `irRouteBetween`, `irCurrentTransportDays`, `irCanTransport`, and `travel`. Travel currently resolves adjacency from `site.routes[]` and calculates duration from `distanceKm` and transport. This behavior is unchanged.

### Save/load

- The save object serializes `state` as JSON through the existing persistence and save-slot flows. `readAutosave`, `readSlots`, `loadSlot`, and `importSave` pass data through `normalizeSave`.
- v0.7.5.2–v0.7.5.5 enrich and validate stable IDs, route endpoints, hierarchy and reference indexes while preserving legacy site IDs and `site.routes[].to` fields. The new shared map layer does not write to saves or add saved fields.

## Minimal preparation implemented

Added `js/game/43-shared-map-data-v0.7.7.1.js` with read-only accessors:

- `irMapSharedData(world)` exposes references to the existing world, region, `region.sites`, `region.routes`, optional hierarchy collections/index, and `IR_BIOMES`.
- `irMapLocationByGeoId(geoId, world)` resolves only a unique stable location ID.
- `irMapConnectionByGeoId(connectionGeoId, world)` resolves only a unique stable connection ID.
- `irMapConnectionsForLocation(geoId, world)` returns a filtered view list of references to existing global connection records.
- `irMapLocationVisibility(geoId, world)` reads current/known/visited/discovered state without mutating it.
- `irMapBiomeForLocation(geoId, world)` resolves the existing biome profile by `site.biomeId`.

These accessors do not clone the location registry, invent coordinates, infer routes from names, or create missing continent/country records. The existing renderer and travel functions are intentionally unchanged; later view work can migrate to the shared accessors in a separately tested step.

## Proposed responsibilities for future views

- **World view:** consume only real world/continent/country/region records and references. The current data is insufficient for an honest multi-region/continent map; add actual generated/saved world-scale geographic records and positions only in a future scoped version.
- **Regional view:** consume the current `region.sites` and `region.routes` through the shared accessors. Stable marker identity is `site.geoId`; connection identity is `route.geoId`; use `x`/`y` only as regional layout coordinates until a real spatial model is approved.
- **Local view:** resolve the selected settlement/landmark by `geoId` and use its existing site/settlement data. Detailed houses, streets, interiors, or local coordinates do not currently exist and must not be fabricated from regional `row`/`col`.
- **Selection contract:** markers carry a stable `geoId`, then resolve the actual site through `irMapLocationByGeoId`; never use display name, list index, or an ambiguous legacy ID as the map marker key.
- **Shared authority:** use `world.region.sites` for location records and `world.region.routes` for map connections. The existing `site.routes[]` compatibility representation still drives travel and must remain synchronized until a later approved migration changes that contract.

## Blockers / explicit non-goals

1. A true world-scale map is blocked by the absence of populated continent/country/multiple-region records and real world-scale positions.
2. A detailed local settlement map is blocked by the absence of local streets/buildings/geometry.
3. The two route representations (`region.routes` and `site.routes`) both exist; current map and travel code use them differently. This subversion documents but does not refactor them to avoid travel/save regressions.
4. Browser-based visual interaction and real `localStorage` reload could not be verified in the current automated environment. Deterministic VM and save-object JSON round-trip checks are not a substitute for a normal-browser playtest.
