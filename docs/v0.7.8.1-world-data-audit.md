# Infinite Realms v0.7.8.1 — World Data Audit

**Status: audit complete; no game-source changes made.** This document records the data model observed in the accepted v0.7.7.9 build and proposes a minimal v0.7.8.2–v0.7.8.8 implementation sequence. The completion gate is to stop here and wait for approval before implementing v0.7.8.2.

## 2. Current authoritative world data

### World generation

Source: `js/game/02-worldgen-v0.2.js:4–46`.

- `irHashSeed()` and `irRng()` provide deterministic seeded randomness.
- `generateProceduralWorld(seedInput, startCircumstance)` normalizes the seed and uses the seeded PRNG.
- The generated region contains a 7×7 grid of **49 site records**. IDs use the legacy pattern `loc-{row}-{col}`; the regional chart `x`/`y`, `row` and `col` are local layout coordinates, not latitude/longitude or world-scale positions.
- The generator assigns a site type (`settlement`, `landmark`, or `wilderness`), optional settlement type, biome, risk, services, discovery/visit fields, and existing route metadata.
- The generator returns one populated `world.region` object with `region.sites[]` and `region.routes[]`, plus `siteId`, `known`, `visited`, `travelCount`, `seed`, `generationVersion: 2`, and `journal`.
- The number of global route edges is seed-dependent; it is not a fixed geography count.

### Stable geographic identities

Source: `js/game/33-stable-geographic-identifiers-v0.7.5.2.js:8–65`.

- `world.id` is derived from the seed using `irGeoWorldId()` when the world lacks an ID.
- Each site keeps its old `site.id` and receives a stable world-scoped `site.geoId` derived from `world.id` and the legacy site ID. Names and array positions are not intended to be identity keys.
- Global route records retain legacy numeric endpoint indexes `a`/`b` and also carry stable route/end-point IDs (`geoId`, `fromGeoId`, `toGeoId`).
- Route IDs are scoped by world identity; the same grid-style legacy site IDs can appear in distinct worlds without sharing the same geographic ID.

### Current hierarchy

Sources: `js/game/34-geographic-hierarchy-connections-v0.7.5.3.js:14–59,68–145`; `docs/v0.7.5.3-geographic-model.md`.

| Entity | Actual current storage | Finding |
|---|---|---|
| World | `state.world` | Owns the current region and reserved hierarchy collections. |
| Continent | `world.continents[]` | Collection exists, but generated records are empty. |
| Country | `world.countries[]` | Collection exists, but generated records are empty. |
| Region | `world.region` | One populated object, not a `world.regions[]` registry. It has nullable `continentId` and `countryId`. |
| Site / location | `world.region.sites[]` | Canonical location records. Every current site references the region with `regionId`; `continentId` and `countryId` are currently null. |
| Settlement | Existing site with `type === 'settlement'` | `settlementId` is an annotation derived from the site's `geoId`; the site is still the location authority. |
| Point of interest | Existing site with `type === 'landmark'` | `pointOfInterestId` references the existing site identity; it is not a duplicate location record. |
| Biome | `site.biomeId`, resolved through `IR_BIOMES` | `world.geography.biomeIds` is a reference/index list, not a second biome registry. |
| Connection | `world.region.routes[]` | Canonical global connection graph used by the shared map/travel adapter. |
| Derived geography index | `world.geography` | Contains IDs/references such as `continentIds`, `countryIds`, `regionIds`, `settlementRefs`, `pointOfInterestRefs`, and `connectionRefs`; it is not an authoritative location registry. |

A read-only generated-world probe using the source modules observed: **49 sites, 0 continents, 0 countries, one region, null region country/continent IDs, 49 unique site geographic IDs, and unique global route IDs**. Counts for route edges and registered settlement/landmark references vary with the seeded content. All current sites had `regionId` pointing to the sole region.

The validator understands generic `parentId` chains for integrity/cycle checking, but that does **not** mean the live generator currently uses a complete `parentId` political hierarchy. Current real links use the explicit fields above.

### Biomes

Source: `js/data/world.js:17` onward.

`IR_BIOMES` defines nine canonical biome IDs: `forest`, `plains`, `mountain`, `swamp`, `desert`, `snow`, `coast`, `river`, and `woodland`. A site stores `biomeId` and a display `biome` label. Existing ecology, resource, hazard, racial-affinity, and monster-habitat code consumes these profiles. Biome is a site/environment classification, not a country, ownership, or political entity.

### Regions defined elsewhere

`js/data/world.js:8–14` contains a legacy `REGIONS` constant with five named sample region definitions. It is not the current generated world's `world.region` and must not be repurposed as a country registry. Its local sample site IDs such as `square` repeat between entries and are not suitable as stable political/geographic IDs.

## 3. Political fields: present versus absent

### Present as reserved relationships

- `world.continents[]` and `world.countries[]` exist and are initialized as empty arrays by `irEnsureGeographicHierarchy()`.
- `region.continentId` and `region.countryId` exist as nullable references.
- `site.continentId`, `site.countryId`, and `site.regionId` exist on current sites.
- Country-to-continent validation is present: a country can reference a unique continent ID.
- `world.geography` derives lists of registered IDs and references from canonical records.

### Not present as live generated political data

The current generated worlds contain no actual records for kingdoms, empires, governments, rulers, capitals, sovereign/territorial ownership, or country boundary geometry. There is no generated `world.regions[]` array, no country polygon/shape, no world-scale coordinates, and no latitude/longitude or elevation model. The current site `x`/`y` are regional layout coordinates only.

The game's existing faction/standing features in `js/game/06-talents-spells-factions-v0.5.js` represent organizations and character affiliation/reputation; they must not be reused as country borders or sovereign ownership.

## 4. Connections, maps, and travel ownership

Sources: `js/game/43-shared-map-data-v0.7.7.1.js`, `44-world-map-v0.7.7.2.js`, `45-regional-map-v0.7.7.3.js`, `46-local-map-v0.7.7.4.js`, `47-travel-route-integration-v0.7.7.5.js`.

- `irMapSharedData()` exposes the existing `world`, `world.region`, `region.sites`, and `region.routes` by reference. It does not create copied geography arrays.
- Map-facing location lookup uses the unique `geoId`, not a display name or array position.
- World view is an atlas/index, not a continental geography map. It respects known/visited data and deliberately does not fabricate continents or borders.
- Regional coordinates are a 7×7-style layout. Route lines correspond to recorded connections and are explicitly schematic, not surveyed roads.
- Local view describes the current site and its existing services/NPC records; its decorative building placement is not saved geographic data.
- Global route edges are authoritative to the integrated travel and map connection adapter; legacy `site.routes[]` adjacency copies still exist for compatibility. Do not add a third route registry. New code should consume the existing graph/helper functions and keep the old records synchronized only where current mechanics already require that.
- A valid travel action changes existing player/world state (current `siteId`, time/energy as applicable, travel count, visit/known state and feed); map scope/selection are transient UI state and must not be stored as territorial facts.

## 5. Save/load and generation behavior

Sources: `js/game/03-stability-v0.2.1.js:7–20,65–78`, `js/game/35-world-generation-integration-v0.7.5.4.js:21–123`, `js/game/50-save-compatibility-v0.7.7.8.js`, `js/data/config.js:5–14`, plus `js/game/02-worldgen-v0.2.js:74–84`.

- The autosave key is `infiniteRealms.v02.autosave`; legacy v0.1 storage keys are still read. Three manual save slots use `infiniteRealms.v02.slots`, with legacy-slot fallback. Saves are browser-local and can be exported/imported as JSON backups.
- `generationVersion: 2` and a valid seed are part of the reusable-world check. The v0.7.5.4 wrapper validates saved world identity/site/routes/hierarchy, reuses a cloned valid saved world, and then ensures the ID/hierarchy metadata rather than blindly replacing it with a newly generated geography.
- Older/incomplete saves pass through the existing normalizer and optional-field compatibility wrapper. Defaults are intended to be idempotent and not overwrite valid values/IDs.
- Same seed + same start circumstance produced identical site/route output in the deterministic generator tests. A different seed yields a distinct world ID. Determinism applies to the current generator version; modifying generation rules can change the layout produced for a seed. That is why loaded saves must retain their saved world data instead of being regenerated on each load.
- A seeded new game is deterministic after its seed is selected. Character creation can choose a fresh seed when the player does not provide one.

## 6. Gaps and risks before political geography

1. **No usable country/continent content yet.** Reserved arrays and nullable links are foundation only; they do not by themselves make a multi-country world.
2. **Single-region assumption.** Existing code expects `world.region` as one object. `world.regions[]` does not exist. Adding a parallel region array without a migration would create duplicate sources of truth. A code search found `world.region` used across 18 game/data scripts (79 literal occurrences); region expansion requires an explicit adapter/migration plan and focused tests, not a silent field addition.
3. **No world-space geometry.** Current positions are regional layout coordinates. Do not draw continental outlines or national boundaries from them as if they were geographic coordinates.
4. **No sovereign polity model.** Kingdom/empire/city-state/tribal territory, government type, ruler, capital, and sovereignty references need a deliberate entity/relationship contract. Existing faction data is a different concept.
5. **No capital/ruler targets are defined.** A future capital should reference an existing settlement `site.geoId`; a ruler should reference an existing, uniquely identified NPC record only if such an NPC exists. Neither should create duplicate location or NPC registries.
6. **Two route encodings remain for compatibility.** Global `region.routes[]` plus local `site.routes[]` are existing forms. New political geography must not introduce another route or location copy.
7. **README release metadata is stale.** The source root README still says v0.7.7.8 although the accepted entry point/build is v0.7.7.9.
8. **External player save untested.** Existing accepted-build-generated saves and an extensive-exploration fixture passed, but no user-exported save was supplied.

## 7. Recommended relationships — no implementation in this audit

The safest minimal model builds on existing canonical data rather than duplicating locations:

- `world.continents[]`: authoritative continent records with stable IDs; country references point to these by `continentId`.
- `world.countries[]`: authoritative geographic country records with stable IDs. Sites use their existing `countryId`; `region.countryId` is set only when the entire single region belongs to one country. If different sites belong to different countries, leave the region-level `countryId` null rather than making it disagree with site references.
- `world.polities[]`: if kingdom/empire/city-state/tribal governance needs separate identity, use one typed political-entity registry rather than separate overlapping `kingdoms[]`, `empires[]`, and `governments[]` registries. Countries reference a polity through one `sovereignPolityId`; polity membership can be derived by scanning countries instead of saving a duplicated country list.
- Political metadata (e.g. `governmentType`, `rulerNpcId`, `capitalSiteGeoId`) should live on the polity only after the field contract is approved. `capitalSiteGeoId` must resolve to an existing settlement site; `rulerNpcId` must resolve to an existing NPC by its actual stable ID. If a valid reference does not exist, leave it null rather than inventing an NPC or location.
- Territorial assignment should be relationships among existing records. Do not create shadow settlement lists, copied site records, or a separate location registry. Do not render a boundary polygon unless actual map geometry exists.
- The future shape of multi-region storage must be decided before adding `world.regions[]`. Either retain the single-region model for the initial country-data step or make a separately tested canonical region-registry migration; do not store the same region twice as `world.region` and `world.regions[0]`.
- Keep world IDs, site geoIds, route geoIds, and existing region/site records stable. Any migration must be repeat-safe, conservative, and must not regenerate the saved world.

## 8. Smallest proposed plan: v0.7.8.2–v0.7.8.8

### v0.7.8.2 — Political geography contract and validators

Document and test canonical record ownership, stable ID rules, `continentId`/`countryId`/`sovereignPolityId` semantics, null/unclaimed cases, reference validation, and the single-region-vs-multi-region decision. No political interaction UI, no generated content, no save migration unless strictly required by an approved schema decision.

### v0.7.8.3 — Seed-stable continent and country records

Populate the existing `world.continents[]` and `world.countries[]` only for newly generated worlds, using stable IDs derived from the world ID plus fixed logical keys (not array indices, display names, or random calls at load time). Keep shape/coordinates out of scope. Existing loaded worlds must remain intact; do not regenerate them to create the records.

### v0.7.8.4 — Assign existing geographic sites to countries

Use each existing site's `geoId` and existing `countryId`/`continentId` relationships. Preserve `site.regionId` and the canonical `world.region.sites[]`; keep `region.countryId` null if site-level country assignments vary. Validate every link and reject duplicate/unresolved IDs. No new site/route registry and no travel or biome behavior changes.

### v0.7.8.5 — Single typed polity registry

If kingdom/empire/tribal/city-state identities are approved, add a single `world.polities[]` with a `type` field instead of parallel registries for each polity type. Link countries by `sovereignPolityId`. This is data foundation only: no faction membership, interactions, diplomacy, wars, reputation, or economic effects.

### v0.7.8.6 — Capital, ruler, and government references

Add validation for `capitalSiteGeoId`, `rulerNpcId`, and `governmentType` only after their exact schema is agreed. Capitals reference an existing settlement site; rulers reference an existing NPC record. No new NPC or settlement is created solely to fill a political field; missing references stay null.

### v0.7.8.7 — Read-only political atlas/index integration

Show actual country/polity records in the World view using the existing shared map-data accessors. Selection is informational and must not mutate world state, reveal undiscovered sites, or pretend to display true borders. Keep the current map geometry unchanged until real world-scale geometry is separately implemented.

### v0.7.8.8 — Save compatibility and acceptance

Test deterministic new-world generation, legacy saves from v0.7.6.6 and accepted v0.7.7.x builds, missing optional fields, extensive exploration, repeat-safe normalization, stable IDs, map selection purity, routes/travel, all existing regression suites, and save/reload. Freeze a baseline only after failures are fixed or explicitly documented. Do not begin the next roadmap stage automatically.

**Out of scope for all of these proposed steps:** combat changes, travel formula changes, biome effects, NPC relationship/reputation behavior, faction membership and political interactions, generated continent polygons/borders without coordinates, and regenerating saved worlds.
