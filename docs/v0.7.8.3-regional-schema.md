# v0.7.8.3 — Regional Hierarchy Data Contract

## Source of truth

- `world.region` remains the canonical primary geographic and route container.
- `world.region.sites[]` remains the one authoritative list of physical locations.
- `world.region.routes[]` and the existing local `site.routes[]` remain the authoritative travel graph. A parent/child relationship does not imply adjacency or reachability.
- `world.region.subregions[]` contains metadata-only child-region records. It must never hold duplicate `sites` or `routes` arrays.
- `world.geography.regionIds` is a flattened reference index generated from the hierarchy. It is not a second registry and contains no full region copies.

## Region record fields

| Field | Meaning |
|---|---|
| `id` | Required stable geographic ID. The primary region keeps `region:${world.id}:primary`; a child is generated as `region:${world.id}:sub:${encode(stableKey)}`. |
| `name` | Display name for the geographic region. |
| `parentRegionId` | The parent geographic region for a nested child. Primary region uses `null`; structural parent must agree with actual nesting. |
| `subregions` | Child region metadata records, possibly empty. |
| `continentId` | Optional reference into existing `world.continents[]`, independent of nested-region parentage. |
| `countryId` | Optional reference into existing `world.countries[]`, independent of ownership and governing polity. |
| `ownerPolityId` | Nullable reference into `world.polities[]` for the political entity that owns the region, if defined. |
| `governingPolityId` | Nullable reference into `world.polities[]` for a political entity that governs the region, which can differ from its owner. |
| `description` | Optional display metadata. |

`ownerPolityId` and `governingPolityId` are separate from parent geography. A null owner and null governor support unclaimed or otherwise politically unassigned regions. No implicit ownership is inferred from a region's parent, country/continent reference, or nearby locations.

## Site region assignment

The site record stays in the primary site's array and carries `site.regionId`. A missing, null, or empty value is treated as belonging to the primary region for legacy compatibility. During normalization the primary region ID is filled in only when the assignment is absent.

An explicit non-empty ID must resolve to exactly one region. `irResolveLocationRegion` returns `status: 'unresolved-region-reference'` for an unresolved explicit ID; it does not guess a replacement. `irValidateRegionalHierarchy` reports unresolved or duplicate references. The existing save-preparation pipeline still has to repair malformed references conservatively; for an unresolved site assignment it uses the only unambiguous container—the primary region—and records a compatibility notice. Valid nested references are preserved by the v0.7.8.3 adapter.

## Nesting and flexible political structure

Region nesting describes geography only. Political relationships use references to `world.polities[]` and are not forced into the same tree. Thus an empire can govern subordinate kingdoms without a kingdom necessarily being a geographic child of the empire; one kingdom can be associated with several geographic regions; and a city-state may reference a compact region without creating a new settlement registry.

The existing `world.countries[]` collection remains geographic hierarchy data, while `world.polities[]` remains the political-entity registry introduced in v0.7.8.2. This release does not establish an automatic one-to-one mapping between those registries or introduce country ownership, government simulation, faction membership, war, diplomacy, or border changes.

## Save compatibility finding

The v0.7.5.5 `ir0755PrepareSaveInput` routine previously forced any `site.regionId` unequal to the primary region ID back to the root. v0.7.8.3 wraps that preparation boundary: it captures only assignments that resolve uniquely in the source hierarchy, calls the legacy checks, then restores a captured assignment only if the same site and region still resolve uniquely in the prepared hierarchy. Missing, unresolved, duplicate, or ambiguous references are not restored. An unchanged save with valid subregion assignments does not receive a false migration flag just because the legacy routine temporarily flattened the reference.

No save-schema version bump, full migration, world regeneration, new site record, or route graph change is introduced.

## Validators and helper APIs

- `irGeoRegionId(worldId, stableKey)` — deterministic child ID helper.
- `irGetGeographicRegions(world)` — returns a flattened list of root/child region objects by reference.
- `irEnsureRegionalHierarchy(world)` — fills absent optional fields and rebuilds the region-ID reference index without silently replacing explicit unresolved IDs.
- `irCreateGeographicRegionRecord(world, input)` — creates a metadata-only region record.
- `irAddGeographicSubregion(world, parentRegionId, input)` — inserts an explicitly requested child region after checking introduced hierarchy errors.
- `irResolveLocationRegion(world, locationRef)` — resolves a site's geographic assignment independently of political validity.
- `irAssignLocationRegion(world, locationRef, regionId)` — changes only the site's geographic `regionId`; does not change routes or political references.
- `irValidateRegionalHierarchy(world)` — checks stable ID uniqueness, parent consistency, no duplicated site/route registries on children, valid country/continent/owner/governor references, and site region references.

The legacy geographic hierarchy validator is retained for its existing ID/route/discovery checks and composed with the regional validator.
